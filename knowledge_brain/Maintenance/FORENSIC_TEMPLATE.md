# Maintenance — Forensic Template

| Symptom | Check first | Likely suspects |
|---|---|---|
| User stuck on maintenance screen even though server flag is off | Confirm the 30s (`startMaintenancePolling`) and/or 60s (`_startPolling`, app-wide) timers are actually firing — check for an exception inside `AppControlNotifier._fetch()` that's being silently caught (`app_control_provider.dart:207-213`), which would leave `state.isMaintenance` stuck at its last value. | Backend `app/control` intermittently failing (timeout, 5xx) — `_fetch()` swallows the error and simply doesn't update state that tick; it'll retry next interval, but a persistently failing endpoint means the screen never resumes even after maintenance is truly lifted. |
| Maintenance lifts but user lands on `/login` despite having a valid session | This is expected behavior per RULE-MAINTENANCE-005 for two of the three entry paths (`app_control_wrapper.dart` mid-session redirect, and the currently-unused `maintenance_gate.dart`) — only the `splash_screen.dart` entry path preserves the login/mpin decision. | Not a bug in this screen — check *which* call site pushed `/maintenance` in this instance (was it splash, or a mid-session redirect?) before assuming it's wrong. |
| Maintenance screen never appears even though server has maintenance mode on | Check whether the interrupted screen even watches `appControlProvider` — only `AppControlWrapper` (wraps entire `MaterialApp`) and this screen itself watch it for redirect purposes; confirm `AppControlWrapper` is actually in the widget tree above the current route (`main.dart:114`). | `AppControlNotifier.initialize()` never called (e.g. `AppControlWrapper` removed/bypassed) — `_initialized` guard (`app_control_provider.dart:64,70-75`) means `initialize()` is a no-op after the first successful call, but if it's never called at all, no polling ever starts. |
| Back button exits the app on iOS unexpectedly | Re-check `_onWillPop()` — it should be Android-only for `SystemNavigator.pop()`; if iOS is exiting too, `Platform.isAndroid` guard logic may have regressed. | Direct regression in `maintenance_screen.dart:81-86` — verify the `if (Platform.isAndroid)` guard is intact. |
| Double navigation / crash on resume ("Navigator locked" or duplicate push) | Check `_hasNavigated` guard — if `build()` somehow runs concurrently or the guard was removed, `_checkResume` could fire `pushNamedAndRemoveUntil` twice. | Regression removing/bypassing the `_hasNavigated` flag at `maintenance_screen.dart:36`, `:71-72`. |
| A payment/withdrawal/SIP action proceeds even though maintenance just started | This is expected given `MaintenanceGate.check()` (the intended pre-transaction gate) is currently called by **zero** modules — see `MODULE_BRAIN.md` §3 Top Risk #2. Any protection today comes from the global `AppControlWrapper` redirect (which only fires once `appControlProvider` state updates, i.e. up to 60s of lag) or server-side rejection. | Missing `MaintenanceGate.check()` call in the initiating screen's submit handler — this is a real gap, not a red herring, if a transaction slips through during a maintenance window. |
